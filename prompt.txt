# SIGNBRIDGE — MASTER IMPLEMENTATION PROMPT

## ROLE AND MISSION

You are a senior full-stack engineer, machine learning engineer, computer vision researcher, and technical product designer.

Your task is to autonomously build a complete, functional, polished hackathon project called **SignBridge**.

SignBridge is a real-time American Sign Language (ASL) recognition and English speech generation application designed to run alongside video conferencing software such as Google Meet, Zoom, and Microsoft Teams.

The product concept is similar to Granola's unobtrusive meeting companion experience, except SignBridge focuses on recognizing a person signing during a video call, producing English captions, and speaking the interpreted text aloud.

You have approximately **24 hours of total development time**.

Your highest priority is to deliver a reliable, demonstrable, end-to-end application, NOT a research prototype with disconnected components.

**Important: You must write actual working code, install dependencies, run tests, debug failures, and deliver a runnable application. Do not stop after producing an architecture document or a list of recommendations.**

Work autonomously. Make reasonable engineering decisions without repeatedly asking me for approval. Ask only when you encounter a genuinely blocking issue requiring credentials, unavailable data, or an irreversible decision.

# 1. PROJECT REQUIREMENTS

## 1.1 Primary user experience

A user opens SignBridge in their browser.

They see a clean, modern interface with a prominent "Start Interpreting" button.

The user can choose one of two video sources:

1. **Webcam Mode:** Capture a local webcam using `navigator.mediaDevices.getUserMedia()`.
2. **Meeting Mode:** Capture a selected browser tab, application window, or display using `navigator.mediaDevices.getDisplayMedia()`.

In Meeting Mode, the user can select a Google Meet, Zoom, or Microsoft Teams window containing a person signing.

The application analyzes the video, recognizes supported ASL signs or expressions, converts recognized sequences into English captions, and optionally speaks those captions using text-to-speech.

The user can see:

- Live video preview.
- Detected hand and body landmarks.
- Recognition status.
- Recognized signs.
- English captions.
- Translation history.
- Confidence estimates where meaningful.
- Audio playback status.
- Video capture status.
- Current processing latency.
- Supported vocabulary.

The application must continue operating without refreshing the page.

## 1.2 Important scope limitation

SignBridge is a hackathon MVP.

Do not claim that the application can translate arbitrary continuous ASL unless the actual implemented model supports and demonstrates that capability.

ASL is a complete natural language with its own grammar, facial expressions, spatial structures, and linguistic conventions.

A classifier trained on isolated signs does not constitute a full ASL translator.

For the MVP, implement a reliable, explicitly limited vocabulary of genuine ASL signs or short expressions, with architecture that can later support continuous recognition.

Do not silently substitute arbitrary hand gestures for ASL.

The UI should describe its capabilities accurately, using language such as:

"Live ASL recognition — supported vocabulary"

The product vision may be described as real-time ASL interpretation, but the implemented MVP must be transparent about its limitations.

# 6. FALLBACK ASL RECOGNITION ARCHITECTURE

If a suitable pretrained model is unavailable, implement a landmark-based temporal recognition system.

## 6.1 Landmark extraction

Use MediaPipe to extract, where supported:

- Left-hand landmarks.
- Right-hand landmarks.
- Upper-body pose landmarks.
- Selected facial landmarks.

Prefer MediaPipe Tasks APIs if they are the supported interface in the installed version.

Use hand, pose, and facial information where practical because ASL meaning can depend on multiple articulators.

At minimum, reliably extract both hands and relevant upper-body landmarks.

If face landmark extraction significantly increases latency, make it configurable.

## 6.2 Landmark normalization

Normalize landmarks to reduce sensitivity to:

- Camera resolution.
- Signer position.
- Distance from the camera.
- Body size.
- Moderate translation within the frame.

Use a stable body-relative coordinate system where feasible.

Preserve information about:

- Relative hand positions.
- Movement trajectories.
- Hand orientation.
- Distances between hands.
- Hand-to-body relationships.

Avoid normalizations that remove linguistically meaningful motion or spatial relationships.

Represent missing landmarks explicitly rather than substituting arbitrary valid-looking coordinates.

## 6.3 Temporal buffering

Maintain a rolling buffer of landmark sequences.

Example configuration:

- Capture approximately 15 FPS initially.
- Buffer approximately 1–2 seconds of observations.
- Use configurable overlapping windows.
- Run recognition at a lower frequency than frame acquisition if necessary.

The exact sequence length must match the selected model or training configuration.

Do not assume every ASL sign lasts the same amount of time.

## 6.4 Temporal classifier

If training a lightweight model, evaluate:

- LSTM.
- GRU.
- Temporal convolutional network.
- Small Transformer encoder.

For a 24-hour hackathon, favor a lightweight GRU or temporal convolutional network unless evidence supports another approach.

Input:

`[batch_size, sequence_length, feature_dimension]`

Output:

`[batch_size, number_of_supported_classes]`

Include an explicit unknown/no-sign class if the training data supports it.

Use appropriate training and validation splits.

Avoid leaking frames from the same recording across training and validation.

Prefer signer-independent evaluation where the dataset permits.

## 6.5 Vocabulary selection

Start with a small, useful vocabulary.

Candidate concepts include:

- HELLO.
- THANK YOU.
- YES.
- NO.
- HELP.
- PLEASE.
- STOP.
- AGAIN.
- UNDERSTAND.
- QUESTION.

These are candidate labels, not guaranteed supported classes.

Only enable a sign if:

1. Genuine ASL examples are available.
2. The implementation can process the required motion.
3. The sign has been tested.
4. Its recognition quality is acceptable for the demo.

Do not assume these English labels uniquely identify a particular ASL sign across contexts.

The actual supported vocabulary must be derived from the available dataset and model.

If only three to five signs can be demonstrated reliably, that is acceptable.

## 6.6 Dataset preparation

If training is necessary:

- Obtain a legally usable dataset.
- Preserve original labels.
- Record dataset provenance.
- Verify label meanings.
- Extract landmarks consistently.
- Cache processed features.
- Create train/validation/test splits.
- Avoid recording-level leakage.
- Train a small classifier.
- Evaluate per-class performance.
- Save model weights and metadata.

Do not train on random synthetic landmarks and present the resulting classifier as genuine ASL recognition.

Synthetic data may be used to test software plumbing but not to establish linguistic accuracy.

If collecting a tiny custom dataset, explain that it is a signer-specific prototype and does not demonstrate generalization.

## 6.7 Unknown-sign behavior

The system must be able to decline to recognize a sign.

When confidence is insufficient:

- Do not invent a translation.
- Do not speak a random word.
- Show a neutral status such as "No supported sign recognized."
- Continue processing subsequent frames.

Use calibrated confidence thresholds where possible.

If probabilities are uncalibrated, label them as model scores rather than reliable certainty estimates.

- Connected.
- Disconnected.
- Reconnecting.
- Processing.
- Error.

# 9. PREDICTION STABILIZATION

A naïve classifier may output the same sign repeatedly for many consecutive frames.

Do not immediately speak every raw prediction.

Implement a prediction stabilization layer.

## 9.1 Stability requirements

A sign should only be emitted when:

- Its model score exceeds a configurable threshold.
- It remains consistent across sufficient observations.
- It passes temporal stability checks.
- It has not already been emitted for the same sign event.

Use a sliding window, voting mechanism, hysteresis, or another appropriate strategy.

## 9.2 Duplicate suppression

Example:

A person signs THANK YOU.

The model recognizes THANK YOU across 12 overlapping windows.

The application should produce one caption and one spoken phrase, not 12 repetitions.

Allow repeated occurrences of the same sign after a meaningful separation or reset.

Do not use a simple permanent deduplication rule that prevents a signer from repeating a word.

## 9.3 Unknown and idle states

Recognize when:

- No signer is visible.
- Hands are missing.
- The signer is idle.
- The model cannot confidently classify the current sequence.

These states must not trigger spoken output.

## 9.4 Caption generation

For the MVP, use a verified mapping between supported ASL class labels and simple English glosses or phrases.

Do not use an LLM to invent grammatical sentences from insufficient sign information.

For example:

`THANK_YOU` → "Thank you."

`HELP` → "Help."

A future natural-language generation layer can be introduced later.

Keep recognition and language generation separate.

Define a recognition interface.

Example:

```python
class SignRecognizer:
    def load(self) -> None:
        ...

    def predict(self, sequence):
        ...

    def get_vocabulary(self):
```

## 13.4 Resource cleanup

Release:

- MediaPipe instances.
- Buffers.
- WebSocket session state.
- Temporary resources.

Ensure that stopping a session does not leave processing tasks running.

## 13.5 Error handling

Handle:

- Invalid frame data.
- Missing model weights.
- Unsupported image formats.
- MediaPipe failures.
- CUDA unavailable.
- Model inference exceptions.
- Client disconnects.

# 18. FALLBACK STRATEGY

Implement the following fallback hierarchy.

## Fallback A — Pretrained model unavailable

Use a small landmark-based classifier trained on genuine labeled examples.

## Fallback B — Training cannot be completed

Reduce vocabulary to the smallest set that can be genuinely validated.

Prefer three working signs over twenty unreliable signs.

## Fallback C — Webcam recognition is inconsistent

Provide a real-inference demo using pre-recorded, appropriately licensed ASL video clips.

The clips must pass through the same recognition pipeline.

Do not substitute expected labels for model predictions.

## Fallback D — Recognition model completely unavailable

Provide a clearly labeled simulated mode demonstrating:

- Video capture.
- Frame transport.
- Caption UI.
- Speech output.
- Session history.

The simulated mode must visibly indicate that recognition is simulated.

Do not claim the system successfully recognizes ASL in this mode.

## Fallback E — Meeting capture fails

Use webcam mode.

Keep meeting capture implemented and document any browser limitations.

## Fallback F — GPU unavailable

Run CPU inference.

Reduce resolution and processing rate if needed.
